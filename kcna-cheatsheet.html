The model everything else hangs off

If only one idea survives to exam day, make it this one.

You write desired state. The control plane writes observed state and works continuously to close the gap between them. That loop never stops and never completes — it just keeps reconciling.

specWhat you want to be true. You own this.
statusWhat is currently true. The system owns this — never write it.
controllerA loop that watches one kind of object and takes action when spec ≠ status.

You saw the same loop in three different places without it being reimplemented once: the ReplicaSet controller replacing a Pod you deleted, the endpoint controller wiring new Pod IPs into a Service you never touched, and the Deployment controller shifting Pods between ReplicaSets during a rollout.

The request path

Every kubectl apply travels this, in order. Know it by name and sequence.

authentication  →  authorization (RBAC)  →  admission control  →  etcd
                                          ├ mutating   (can change your object)
                                          └ validating (can only accept/reject)

You met mutating admission without looking for it: the API server added kubernetes.io/metadata.name to your namespaces. What you submit is not necessarily what gets stored.

Manifest anatomy

Four top-level fields, every object, no exceptions worth caring about.

apiVersionWhich API group and version this object's schema comes from.
kindThe object type.
metadataIdentity — name, namespace, labels, annotations.
specDesired state. ConfigMap and Secret use data instead.

YAML list indentation

The most common Kubernetes YAML error there is. The - counts as indentation — sibling keys align under the first key after the dash, not under the dash.

containers:
  - name: web        ← keys align at this column
    image: nginx     ✓
    ports:
      - containerPort: 80

  - name: web
  image: nginx       ✗ parse error — dedented out of the list item

Multi-line strings

The block scalar | preserves newlines — used constantly for embedded files, scripts and certs.

data:
  index.html: |
    <html>
      Hello world!
    </html>

Object reference

The five you wrote, plus the one the Deployment made for you.

KindapiVersionScopeWhat it does
Namespacev1clusterScopes object names; a handle for RBAC and quotas. Not a network or security boundary.
Podv1namespacedSmallest schedulable unit. One or more containers sharing an IP, port space and volumes.
ReplicaSetapps/v1namespacedKeeps exactly N Pods matching its selector alive. You never write one by hand.
Deploymentapps/v1namespacedManages ReplicaSets to give you rolling updates and rollback.
Servicev1namespacedStable virtual IP + DNS name, load-balancing across Pods that match its selector.
ConfigMapv1namespacedNon-secret config, injected as env vars or mounted as files.

Cluster-scoped vs namespaced

A cluster-scoped object cannot sit inside a namespace. Setting metadata.namespace on one is a category error.

# ask the cluster rather than memorising:
kubectl api-resources --namespaced=false   # Namespace, Node, PersistentVolume,
                                           # ClusterRole, ClusterRoleBinding, StorageClass, CRD
kubectl api-resources --namespaced=true    # everything else

This split is exactly why RBAC ships two pairs: Role/RoleBinding (namespaced) and ClusterRole/ClusterRoleBinding (cluster-wide).

API groups

No pattern to infer — kubectl explain <kind> gives you the right value.

v1The core group, which has no prefix. Pod, Service, ConfigMap, Secret, Namespace, Node.
apps/v1Deployment, ReplicaSet, StatefulSet, DaemonSet.

The ownership chain

Three layers, and the names encode the hierarchy.

Deployment
Manages versions. Creates a new ReplicaSet whenever the Pod template changes.
creates & owns ↓
ReplicaSet
Counts Pods matching its selector. Fewer than desired → create. More → delete. That is its entire job.
creates & owns ↓
Pod
The workload. Gets an ephemeral IP that dies with it.
my-deployment                    ← you named this
my-deployment-54bf7b886b         ← + hash of the Pod template
my-deployment-54bf7b886b-fdkp6   ← + random per-Pod suffix

The template hash is the rolling-update mechanism. Change the template → new hash → new ReplicaSet → Pods shift from old to new. The old ReplicaSet is kept at 0 replicas, which is why rollout undo is near-instant: it just scales the old one back up.

ColumnMeans
READYPods passing their readiness check. A Pod can be Running but 0/1 ready — and it receives no traffic.
UP-TO-DATEPods running the current template.
AVAILABLEReady, and stayed ready long enough to count.
Immutable

A Deployment's spec.selector cannot be changed after creation. Changing it means delete and recreate.

Selector syntax differs by object

A genuine inconsistency in the API. Services predate the newer selector syntax.

# Deployment / ReplicaSet
selector:
  matchLabels:
    app: hello

# Service — a plain map, no matchLabels
selector:
  app: hello

Services & DNS

Pods get ephemeral IPs. Services are how anything finds anything.

A Service holds a stable virtual IP — no interface anywhere owns that address, and you can't ping it. It exists only as packet-rewriting rules that kube-proxy programs on every Node. An EndpointSlice is auto-maintained with the IPs of Pods currently matching the selector.

Decoupled by design

A Service does not know its Deployment exists. It matches labels on Pods, full stop — any Pod carrying the right label gets traffic, whoever created it. Deployment→Pod and Service→Pod are independent relationships, both built on labels.

Empty endpoints with healthy Pods = your selector doesn't match your Pod labels. The single most common Service bug.

The four types

TypeBehaviour
ClusterIPDefault. Internal-only virtual IP.
NodePortClusterIP plus a high port (30000–32767) opened on every Node.
LoadBalancerNodePort plus a cloud provider LB. This is what an Azure Load Balancer is, behind AKS.
ExternalNameNo proxying at all — just a DNS CNAME to an external host.

Each builds on the one above it. That layering is examinable.

port vs targetPort

portThe port the Service listens on — what clients dial.
targetPortThe port on the Pod to forward to.
containerPortPure documentation. Opens nothing, publishes nothing, firewalls nothing.

Cluster DNS

<service>.<namespace>.svc.cluster.local

my-service                                # from inside the same namespace
my-service.playground                     # from another namespace
my-service.playground.svc.cluster.local   # fully qualified

Short names resolve because every Pod gets a search domain for its own namespace. CoreDNS holds a record for every Service. Learn this format verbatim — it comes up directly.

Pod CIDRPod IPs — 10.42.0.0/16 on this k3s cluster. Ephemeral.
Service CIDRService ClusterIPs — 10.43.0.0/16. Stable for the Service's lifetime.

Config & secrets

One image, many environments. Config is injected at runtime, never baked in.

Two ways to consume a ConfigMap — and they behave differently

Env varMounted volume
Appears as$MY_VARa file on disk
Read whenonce, at container startwhenever the app reads the file
On ConfigMap changestale until the Pod restartsupdates in place, within ~a minute

Environment variables are handed to a process once at exec time and can never change afterwards. That's a Linux fact, not a Kubernetes limitation. Use kubectl rollout restart to pick up new env values.

Gotcha

A volume mounted with subPath does not receive updates, even as a file. This one costs people entire afternoons.

volumes vs volumeMounts

volumes sits at Pod level and declares what's available. volumeMounts sits at container level and says where that container sees it. The name links them.

spec:
  containers:
    - name: web
      volumeMounts:                          # container level
        - name: html
          mountPath: /usr/share/nginx/html
  volumes:                                   # Pod level — sibling of containers
    - name: html
      configMap:
        name: hello-config
Exam favourite

A ConfigMap is plaintext in etcd — readable by anyone with get configmap in that namespace.

A Secret is base64-encoded, not encrypted, by default. Base64 is an encoding, not a security control. The intuitive answer here is the wrong one.

kubectl

Grouped by what you're trying to do.

Before anything that mutates

kubectl config current-context           # which cluster am I about to hit?
kubectl config get-contexts

# make the safe context the default — PowerShell profile
function kp { kubectl --context rancher-desktop @args }
Safety

This kubeconfig holds two contexts: rancher-desktop (the sandbox) and SHAREDSERVICES-01-AKS (a real employer cluster). Every apply, delete, scale or edit gets an explicit --context rancher-desktop. Relying on the active context is luck, not safety.

Validate before applying

kubectl apply -f f.yaml --dry-run=client   # YAML + schema, locally. Never touches the cluster.
kubectl apply -f f.yaml --dry-run=server   # the API server validates for real, persists nothing
kubectl diff  -f f.yaml                    # the `terraform plan` of Kubernetes

# catch silent drops: compare what you sent to what would be stored
kubectl apply -f f.yaml --dry-run=server -o yaml

Dry-run creates nothing. The word created in its output is a simulation — that's why the object doesn't appear afterwards.

apply vs create

create -fImperative. "Make this." Fails if it already exists.
apply -fDeclarative. "Make reality match this file." Creates or patches. Idempotent.

apply in a loop against a git repo is essentially what Argo CD and Flux do — which is why GitOps is built on it.

# create is still useful as a YAML generator:
kubectl create deployment demo --image=nginx:1.27-alpine --dry-run=client -o yaml

Inspect

kubectl get deploy,rs,pods -n playground        # all three layers at once
kubectl get pods -o wide --show-labels          # IPs, nodes, labels
kubectl get pod <name> -o yaml                  # see status/ — written by the system
kubectl get svc,endpointslice -n playground     # is the Service actually wired up?

kubectl describe pod <name>                     # ← Events at the bottom. Read these first.
kubectl logs <pod>
kubectl exec -it <pod> -- sh
kubectl exec deploy/<name> -- printenv VAR      # no quoting to get wrong

kubectl explain deployment.spec.template        # the schema, from the cluster itself
kubectl api-resources

Change things

kubectl apply  -f k8s/                          # the correct default
kubectl delete -f k8s/01-pod.yaml               # delete by file, not by name

kubectl scale deploy/x --replicas=5             # ⚠ drift — next apply reverts it
kubectl rollout restart deploy/x                # replace Pods without editing the manifest
kubectl rollout status  deploy/x
kubectl rollout history deploy/x
kubectl rollout undo    deploy/x

kubectl port-forward svc/my-service 8080:80     # debug tunnel; bypasses Ingress entirely
kubectl run tmp --rm -it --image=curlimages/curl --restart=Never -- sh
Windows shells

cmd.exe does not treat ' as a quote character — use "double". PowerShell wants 'single', to stop it expanding $VAR before kubectl sees it. Or sidestep both with -- printenv VAR and -- cat file.

Where Kubernetes stayed quiet

The recurring theme of the session, and the most expensive habit to build. Every one of these applied cleanly and did the wrong thing.

  • metadata.namespace on a cluster-scoped object Silently dropped. No error, no warning — the stored object simply doesn't have it, and your file now claims an intent the cluster is ignoring.
  • env: - name: GREETING  (no valueFrom) Schema-valid. value is optional and defaults to empty string, so Pods start happily and the variable is blank.
  • --dry-run printing "created" Nothing was created. The word is part of a simulation, and the object never existed.
  • kubectl scale against a committed manifest Works instantly, then the next apply silently reverts it. Same failure mode as editing something in the Azure Portal that Terraform owns.
  • A Service whose selector matches nothing A perfectly legal object with an IP and no endpoints. Connections just fail. Indistinguishable at a glance from a Service whose Pods are simply gone.
  • image: nginx (unpinned tag) Resolves to :latest — not a version, a moving target. The same manifest gives different results on different days.

The habit: when something "works" but doesn't behave, diff what you submitted against what was stored. --dry-run=server -o yaml settles it in seconds.

Flagged for the exam

Points from this session that KCNA asks about directly.

ClaimThe right answer
A namespace isolates workloads from each otherNo. It scopes names and anchors RBAC/quota. Pods across namespaces can reach each other freely until a NetworkPolicy says otherwise.
Secrets are encryptedNo. Base64-encoded by default. Encryption at rest is a separate thing you enable.
Kubernetes schedules containersNo. It schedules Pods onto Nodes. The runtime on that Node starts the containers.
containerPort publishes a portNo. It's documentation. The process listens on whatever it binds.
A Service routes to a DeploymentNo. It routes to any Pod matching its label selector, regardless of owner.
Rollback re-deploys the old versionNo. It scales the old ReplicaSet back up — which is why it's near-instant.
